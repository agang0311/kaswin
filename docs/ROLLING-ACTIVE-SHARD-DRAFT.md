# 单活动片滚动分片设计

本文只写业务规则与设计推导。账本字节偏移、入口ABI、固定输入输出布局、Indexer接口和客户端约定见[实现规格](ROLLING-ACTIVE-SHARD-IMPLEMENTATION.md)。源码候选位于[experiments/rolling](../experiments/rolling/README.md)，已按本版同步尾片合并、WIN字段和终局退出规则。全部规则均未经编译、测试、VM或链上验证。

## 1. 总体结构

一轮只有一个可以售票的片，它同时是全轮管理者，**不单独设置C**。每片最多256笔购买；第256笔购买在同一笔交易里封存本片，并把管理职责交给新建的下一片。全轮封盘后，最后一片继续管理开奖、派奖和退款，直到全轮结清。

整轮所有状态输出共用一个CID。同CID只表示属于同一轮，不代表角色或动作合法；角色由账本角色字节区分，阶段由固定模板区分：

| 模板 | 角色 | 职责 |
|---|---|---|
| SALES | 管理（0x01） | 售票、换片、全轮封盘 |
| SEALED | 管理 | 等待开奖或超时转退款 |
| WIN | 管理 | 保存赢家，按顺序派奖 |
| REFUND | 管理 | 按顺序退款 |
| FROZEN | 冻结（0x00） | 保存满片目录和票款，只能随WIN／REFUND管理片一起被消费 |

| 容量项目 | 规则 |
|---|---|
| 有票满片 | 最多256个（S0～S255），每片固定256条记录 |
| 最终空管理片 | S255售满后创建S256，目录为空，不再售票，只负责封盘与结算 |
| 全轮购买记录 | 最多65,536条 |
| 全轮票数 | 创建时固定ticketCap，最大10,000,000张；一条记录可买多张 |
| 同时存在的状态UTXO | 最多257个（256个冻结片＋1个管理片） |

## 2. 账本内容

### 管理片

```text
管理账本 = 固定头部（配置、角色、N、阶段字段）
         || N项旧片索引（32字节冻结脚本哈希 + 4字节全局累计票数终点）
         || 本地购买目录（4字节本片累计票数终点 + 32字节买家公钥）
```

- N为2字节，取值0～256，既是旧片数量，也是当前管理片的逻辑编号，并用于切分索引与目录。N<256时本地目录有0～255条；N=256时必须为空。
- 全轮配置只保存在管理片：创建者公钥、ticketPrice、ticketCap、minTickets、closeEligibleDaa。所有管理后继都保持不变。
- 阶段字段：WIN保存32字节赢家公钥和2字节派奖游标p；REFUND保存退款游标r、c，各为2字节。中奖票号只在开奖交易内计算，WIN不保存。
- 索引第j项就是逻辑片S_j。片编号、片内票数、全轮票数和购买次数都不另存：

```text
n_local      = 本地目录条数
localTickets = 本地目录末条累计终点（空目录为0）
baseTickets  = 索引末项累计终点（N=0时为0）
T            = baseTickets + localTickets        全轮票数
购买次数      = 256 × N + n_local
```

例：索引为`[hashA,1000]、[hashB,2600]`，本地已售80张，则A、B和当前片分别对应全局第1～1000、1001～2600、2601～2680张。

### 冻结片

冻结数据只有`角色0x00 || 256条购买记录`，共9,217字节，不含配置、CID、押金、片编号或游标。程序部分只负责核验同一交易中的管理片（第9节）。票价从管理片读取，轮次身份从实际UTXO的CID取得。

### 配置范围

| 字段 | 规则 |
|---|---|
| ticketCap、minTickets | `3 ≤ minTickets ≤ ticketCap ≤ 10,000,000` |
| ticketPrice | 至少1 KAS，且`ticketPrice × ticketCap + 4 KAS ≤ 90,000,000 KAS`；ticketCap=10M时最高8.9999996 KAS |
| 押金 | 全轮一份，4 KAS |

金额一律按整数sompi计算。minTickets下限为3，配合1 KAS最低票价，可保证没有旧片的单片轮次奖池至少3 KAS（理由见第7节）。

## 3. 售票与换片

普通购买：`S_i + 付款人资金 → S_i'`。追加一条记录，累计终点增加q，票款增加q×票价；要求`q ≥ 1`、`T + q ≤ ticketCap`、`N < 256`。

第256笔购买：

```text
S_i（已有255条）+ 第256笔购买资金
    → S_{i+1}：空目录、继承全部索引并追加S_i、全轮押金
    + S_i（冻结）：完整256条目录、本片全部票款
    + 可选找零
```

```text
S0售满 → 封存S0，创建S1，S1记录[S0]
S1售满 → 封存S1，创建S2，S2记录[S0, S1]
……
S255售满 → 封存S255，创建S256，记录[S0 … S255]；S256不再售票
```

换片约束：

- 索引前缀原样继承，只在末尾追加**冻结后脚本**的哈希和本次购买后的全轮累计票数，N恰好加1。
- 冻结片押金为0，持有本片全部票款；押金只转入新管理片，不复制。
- 所有后继中只有一个管理片；冻结片没有售票、换片或发行管理片的入口。
- 同一管理输入只能被一笔交易消费，两笔竞争的第256笔购买只有一笔会被接受。

票数达到ticketCap即停止购买。若此时本片恰好写满256条，仍按上式换片，再由新的空管理片封盘。

## 4. 资金归属

| 状态 | 持有资金 |
|---|---|
| 管理片 | 押金＋本片尚未结算的票款 |
| 未结算冻结片 | 本片全部票款，押金为0 |
| 部分退款冻结片 | 同一脚本，只持有未退记录的票款 |

- 票权和收款权以购买目录中的公钥为准。协议允许付款人与目录公钥不同；标准客户端用同一钱包出资和持票。
- 赢家、买家、创建者、执行者和找零的普通收款只使用32字节公钥的Schnorr P2PK，不带covenant绑定。
- 封盘、开奖、超时转退款和空轮退押金的网络费由执行人另行出资，不设奖励。派奖和退款的网络费分别从对应奖池或退款费池支出。

## 5. 全轮封盘

closeEligibleDaa只开放封盘资格，不是硬性停售时间：

| 状态 | 购买 | 封盘 |
|---|---|---|
| 未到时间，票数和记录都未满 | 允许 | 不允许（达到minTickets也不行） |
| 已到时间，仍有容量 | 允许 | 允许，与购买竞争同一个管理输入 |
| 票数或记录已满 | 不允许 | 立即允许 |

封盘只消费管理片，冻结片保持不动。按全轮票数T分支：

| T | 结果 |
|---|---|
| 0 | 押金全额退还创建者，本轮结束 |
| 0 < T < minTickets | 进入REFUND，r=c=0 |
| T ≥ minTickets | 进入SEALED |

封盘后不能再售票、追加记录或改变原始票权。判断空轮必须看全轮T，不能只看当前片是否为空。

## 6. 开奖

### 时间

设d为SEALED管理UTXO的共识DAA：

| SEALED年龄（DAA） | 可执行操作 |
|---|---|
| < 100 | 等待 |
| 100～431,999 | 凭完整PASS-A证明开奖 |
| ≥ 432,000 | 开奖，或超时转REFUND；两者竞争同一个输入 |

形成WIN后不能再转退款；形成REFUND后不能再开奖。冻结片的满片时间不参与计时。

### 随机数与抽样

```text
seed = blake2b256("KASWIN_ROLLING_DRAW_V1"
                  || CID || 输入0的outpoint（txid、index）
                  || d+100 || PASS-A目标块哈希 || 序列承诺)

x = blake2b("KASWIN_V2_SAMPLE" || seed || 8个零字节) 的前7字节（小端）
limit = 2^56 − 2^56 % T
x < limit：中奖票号 t = x % T（从0起）
x ≥ limit：抽样拒绝，不能开奖，只能等待超时转退款
```

输入0的outpoint通过交易ID承诺了SEALED的完整脚本和全部票权，因此不必另外哈希一份票权摘要。种子不包含开奖交易自身的任何可变内容，执行人无法换样本重抽。

### 定位赢家

构建器提交中奖片位置j和片内记录位置i作为提示，合约自行算出t后核验：

- 片区间`[上一项累计终点, 本项累计终点)`必须包含t；j=N时使用管理片本地目录，区间终点为T。
- j<N时提交该冻结片的完整脚本，其哈希必须等于索引第j项；只读取，不消费该片。
- 第i条记录的本地区间必须包含`t − 片起点`，赢家公钥取自该记录。

提示错误只会让交易失败，不能改变t或赢家。开奖交易只把管理片转为WIN（保存赢家公钥，p=0），不付款，管理片金额不变。

## 7. 派奖

WIN管理片保存派奖游标p，即已付清的旧满片数量，取值0～N。若N>0且原始尾片奖池低于3 KAS，存续WIN必须满足p<N；最后一批直接终止，不产生p=N的管理后继。

**普通批次**：消费WIN管理片和从p开始的连续k片（1≤k≤16），p增加k。

```text
执行者奖励 = k × 1 KAS
赢家净奖金 = 本批票款 − k × 1 KAS − 本笔网络费（≤ 1 KAS）
管理片金额保持不变
```

**最后一片**按其奖池（本地票数×票价）结算：

| 条件 | 结算方式 |
|---|---|
| N>0，尾片奖池 < 3 KAS（含空片） | 与到达p=N的那一批一起结清：赢家得到本批票款＋尾片奖池−k KAS−网络费，押金退还创建者，管理片终止；尾片不另计奖励 |
| N>0，尾片奖池 ≥ 3 KAS | 旧片全部付清（p=N）后单独结算：赢家得到尾片奖池−1 KAS−网络费，押金退还创建者，执行者得到1 KAS |
| N=0 | 按上一行单独结算；minTickets≥3保证奖池至少3 KAS |

3 KAS＝1 KAS奖励＋最多1 KAS网络费＋至少1 KAS净奖金。奖池低于这个数时，不能保证在最高1 KAS网络费下仍留下至少1 KAS净奖金，因此协议统一要求合并；这不表示较低手续费下数学上绝不可能单独付款。合并时不会出现p=N的存续管理片，也就不需要单独的空片退出交易。

奖励合计：每个冻结满片1 KAS，尾片奖池≥3 KAS时再加1 KAS。满载时S256为空，合计256 KAS。所有付款都付给WIN中保存的同一赢家，执行者不能更换收款人。

## 8. 退款

REFUND管理片保存两个2字节游标：r为已退完的旧片数，c为当前片已退记录数。按S0、S1……顺序处理，每笔消费管理片和当前旧片S_r，固定退32条：

```text
(r,0) → (r,32) → … → (r,224) → (r+1,0)
```

设v为票价，T_r为本片票数，Q(c)为本片前c条的累计票数：

```text
冻结片应有余额 = (T_r − Q(c)) × v
本批票款B      = (Q(c+32) − Q(c)) × v
每条退款       = 本条票数 × v − 0.02 KAS
执行者        = 32 × 0.02 KAS − 网络费（≤ 0.5 KAS）
```

前7批生成同一脚本、余额减少B的冻结后继；第8批不再生成后继。处理旧片期间，管理片金额保持不变。每片共8笔，满载时旧片退款共2,048笔。

**最后一片**的判断与派奖相同：

| 条件 | 结算方式 |
|---|---|
| N>0，尾片奖池 < 3 KAS（含空片） | S_(N−1)的第8批同时退还尾片全部记录（最多2条，每条扣0.02 KAS），押金全额退还创建者，管理片终止；执行者得到(32＋尾片记录数)×0.02 KAS−网络费 |
| 其他情况 | 旧片全部退完（r=N）后，按现有规则退管理片自身：每批最多32条，每条扣0.02 KAS，末批再从押金扣0.02 KAS（创建者收回3.98 KAS）；费池不足时执行者可以补费 |

旧片没有全部退完时，不得释放押金或终止管理片。合并判断始终使用原始本地目录推导的票款，不随退款后的剩余余额变化。符合合并条件时，存续REFUND必须满足r<N；最后旧片的第8批同时结清本地责任并终止，不产生r=N的管理后继。真正零票轮次在CLOSE时已经结束，不进入零票REFUND。

## 9. 核验分工与同哈希冻结片

**冻结片只核验三件事**：输入0是同CID的管理片；该管理片的模板是固定的WIN或REFUND模板，从输入0的真实签名脚本读取并核对P2SH；自身不授权任何后继。

**管理片负责全部业务**：目标冻结片与索引项匹配、应有金额、游标推进、每个收款人及金额、全部后继和普通输出、网络费上限。冻结片的剩余后继也由管理片授权。

**相同冻结哈希**：两片目录逐字节相同时，冻结脚本、哈希和地址都相同；不同轮次之间也可能相同。处理规则：

- 索引按位置保留每一项，不能按哈希去重。
- 处理第j项时，可以使用任意一个本轮CID、哈希匹配且金额等于应有金额的未花费输出；每次各消费一个不同的outpoint。
- 部分退款片的余额严格小于完整片，不能用同哈希的完整片顶替。按顺序退款保证任何时刻至多存在一个部分退款片。
- 跨轮同哈希只共享原文，资金消费始终核对本轮CID。

## 10. 数据可用性

P2SH只承诺哈希，开奖、派奖和退款都需要完整原文：

- 每个冻结片都能由它的换片交易还原：前255条在输入0管理片的签名脚本中，第256条来自该笔购买的数量和买家公钥。管理片原文在每次被消费时也会出现在交易中。
- 普通节点会裁剪历史交易，因此由Indexer持续保存全部冻结原文和最新管理原文，并按outpoint记录余额与消费关系。Indexer只提供可核验的材料，不决定赢家、收款人或金额。
- 派奖和退款按设计严格顺序推进：当前片原文缺失时，后续结算暂停，等待从Indexer、归档节点或其他副本恢复。不能跳片、补零或更换赢家，也不能把WIN改成退款。

## 11. 不变量

1. 任一时刻全轮最多一个管理片；冻结片不能售票、发行管理片或自行退出。
2. 索引只追加，每一项对应一个实际发行、含256条记录和足额票款的冻结片。
3. 全轮票号从0到T连续、不重叠；结算过程中原始目录和索引不变。
4. 资金守恒：管理片＝押金＋本片未结票款，冻结片＝本片未结票款；每笔交易输入＝输出＋网络费。
5. WIN与REFUND单向互斥，赢家确定后不再改变。
6. p、r、c只按规定推进，每次推进都对应实际付款；全部票款结清后，管理片才能释放押金并终止。
