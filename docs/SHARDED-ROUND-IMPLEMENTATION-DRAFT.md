# 分片扩容历史方案

当前主线统一见[单活动片滚动分片设计](ROLLING-ACTIVE-SHARD-DRAFT.md)：不单独设置C，唯一活动片S_i保存全部旧片索引，满256笔时封存并创建S_{i+1}。

以下保留早期独立C协调和并行分片讨论，均为历史 **DRAFT / BLOCKED**，不代表当前设计或现行合约能力。旧顺序方案详见[历史草案](SEQUENTIAL-SHARDS-DRAFT.md)。

## 历史中间方案：独立C协调顺序分片

本节是旧C方案；下方第1–14节及25问／14材料／8项审查描述更早的“BUY不消费C”并行候选。两者仅供历史参考。

候选流程：

```text
FIRST_BUY: C_SALES + 买家资金 -> C_SALES' + S0（首笔记录）+ 规定找零
BUY_i:     C_SALES + S_i + 买家资金 -> C_SALES' + S_i' + 规定找零
ROLL_BUY:  C_SALES + 买家资金 -> C_SALES' + S_next（首笔记录）+ 规定找零
CLOSE:     C_SALES -> C_SEALED
DRAW:  C_SEALED -> 唯一WIN或合法REFUND决策
结算:  C决策与对应S_i共同消费以授权派奖/进入本片退款
```

- C每次BUY原子核验并同步全轮票数及对应片的记录数、账本承诺、金额摘要；未操作片的摘要保持不变。C不复制所有购买目录，也不直接承诺同一交易尚未确定的新后继txid，避免自引用；当前位置仍需定位与核验。
- 所有S_i的BUY都必须验证真实C_SALES输入及合法后继，不能有绕过C的售票入口。此前提成立时，只封C即可在协议层阻止各片继续售票，不必一次花费全部Sn。CLOSE与基于旧C的BUY互斥；冻结后不可任意增加/移除片或改变票权。
- C把全轮统计和片承诺绑定进链上状态，可降低对Indexer自行汇总正确性的依赖；**不消除C/S账本前像与历史材料的可用性依赖**。P2SH哈希不是完整原文，缺数据仍可能阻断开奖、派奖或退款。
- 同轮BUY仍争用C；分片分散的是目录/资金规模，不能宣称提高并发TPS。每买同时携带C与一个Sn，C摘要表也会增加字节、执行与费用，需完整资源测量。
- 原先“每步等10秒，65536次购买约7.59天”的假设在此路线下仍成立；10秒并非Kaspa强制的逐操作间隔，实际吞吐另测，不能靠假设未确认链就抹去串行取舍。
- 用户现已明确按顺序使用活动片，片满后创建下一片，不预建全部空片；C记录全部已创建片的摘要与位置，Sn记录本片目录。活动片可用“与当前C同交易的指定输出”定位，旧片可用固定outpoint；任何只更新C的转换都须规范化相对引用。换片不消费旧满片是待证明候选；数据暂不可得、全轮已满或已封盘都不能冒充“片满”另开片。详见新草案第3–4节。
- 用户界面继续合并为一个轮次。身份初始化、多输入角色校验、单一WIN/REFUND互斥、数据恢复及无人推进/费用不足退出依旧是未闭合项；当前合约不能原样组装使用。


现行工作区（`kaswin/`）为V2.0.2 / `ed0387c9e77bb4e0a8f1f4654a326c316d83663f455283ec6a046a095c94856d`，单轮单状态；不能再把较早V2.0.1草案当当前发布状态。历史存档 `<legacy-v202-archive>`（与工作区同级的目录）保持只读。

## 1. 证据与边界

遵循工作空间[核心架构规范](../../knowledge/contracts/core-architecture-spec.md)和[25问模板](../../knowledge/contracts/architecture-preflight-template.md)。以下只有固定源码核对（S）与候选分析，无新L/V/N结论。

一手固定来源：

- rusty-kaspa v2.1.0 `01b532e8b553523216471682649693af92f0fd16`：[covenants context](https://github.com/kaspanet/rusty-kaspa/blob/01b532e8b553523216471682649693af92f0fd16/crypto/txscript/src/covenants.rs)、[CID hashing](https://github.com/kaspanet/rusty-kaspa/blob/01b532e8b553523216471682649693af92f0fd16/consensus/core/src/hashing/covenant_id.rs)、[opcodes](https://github.com/kaspanet/rusty-kaspa/blob/01b532e8b553523216471682649693af92f0fd16/crypto/txscript/src/opcodes/mod.rs)。input内省只针对交易实际输入；一个输出只有一个authorizing input。genesis绑定须重算CID，不加入continuation计数，不能只数OpCov/OpAuth就当输出都被检查。
- SilverScript v1.0.0 `3ed973335b59269293564805cc2c58a14595ec03`：[statement lowering](https://github.com/kaspanet/silverscript/blob/3ed973335b59269293564805cc2c58a14595ec03/silverscript-lang/src/compiler/compile/statement.rs)。RequireTxDaa使用CLTV下限；不是可读取的实时区块DAA上界。不能用交易自己填的lockTime较小证明现在还没到截止时间。
- 当前[架构](ARCHITECTURE.md)及 `contracts/{open,sealed,refunding}.sil`：activeInputIndex=0、唯一状态、256条目录、局部32条退款。不能原样放进多状态交易并声称可用。

没有自动升级共识或编译器pin。当前节点激活、网络参数、分片脚本预算/质量及跨合约可执行性需后续专门核验。

## 2. 产品契约：用户只操作轮次

用户路由仍为一个轮次身份R；页面只展示规则、票价、总票数、票款/预计净奖金、我的票、开奖结果、到账/退款进度。Sn编号、片内游标、冻结位图及调度只在开发诊断或可选链上证据中出现。

用户阶段：准备中 → 售票中 → 封盘中 → 待开奖 → 奖金发放中/退款中 → 已结束。C的一个终局标志不代表所有款项已到账；实际accepted付款完成后才升级对应状态。

- 购买：输入张数、审阅金额和网络费、钱包批准。默认一次购买只选一个有足够余量的片，保持一次签名/交易。
- 本片余量不足时先换可容纳整笔数量的片；必须拆成多笔时显示交易笔数、费用和部分完成风险，不静默拆单或代签。
- 售票期间不承诺全局连续的实时票号。收据绑定R、分片内部身份、已接受BUY及票权区间；页面只显示票数和购票凭证。若需全局连续展示号，在全部封盘后按固定分片顺序生成，不改变既有票权。
- 分片可隐藏，不能隐藏网络费、重新签名、部分到账、未决状态或真实资金风险。

## 3. UTXO对象、身份与初始化

首版研究固定有界M，不在售票期间增加或删除分片。每片最多256条购买记录；每次BUY可买多票，故 `M×256` 是记录容量，不是票数上限。

| 对象 | 共识职责 | 生命周期 |
|---|---|---|
| 控制C | 不可变轮次规则/片集合、已冻结摘要与票数、唯一决策及处理位图、独立运维储备 | 初始化、收集、READY、WIN或REFUND、协调终止 |
| 售票S_i | 片内票数/目录、购票本金、押金；阶段门控 | PREPARED/OPEN→FROZEN→付款终止或REFUNDING→终止 |
| 普通资金 | 买家票款、创建押金、执行者付费/赞助 | 普通签名输入与找零 |
| 普通付款 | 赢家奖金、买家退款、押金返还、执行费 | 协议终止后普通UTXO |

首版不增加结果凭证UTXO，也不做奖池归集：先使用同交易的C输入直接证明全轮决策。

**身份候选**：外部R取稳定的初始C Covenant ID（网络和Profile同时域隔离），片身份为 `(R, role=SALE, i)`。可研究同一family内C/S共用一个带严格role分派的模板：先创建唯一C，再由C受约束生成各片；这样不要求两个独立模板互相嵌入对方hash，也不要求创世脚本把自己的CID写进哈希前像。此候选可能增大脚本/ABI，尚未编译验证，不是已选最终实现。

无论同family还是分开模板，必须证明：合法初始C仅一个；每个i只发行一次；C/S更新只能产生规定role与数量；C决策不被S伪造；只写相同R不能创造合法分片。genesis与各role解析、同交易多role检查、所有后继输出必须完整审查。不得用“CID一致”替代模板和状态约束。

初始化可以分批进行，但片集合/容量分配必须预先承诺，只有经过认证的片才能接纳购买。准备失败时已锁押金、已经产生的片如何退回必须定义；不得把未完成初始化放到用户面前宣布成功。

全轮票数上限候选为预分配片配额之和，各片链上独立检查自身额度。售票期间的配额搬移不做；这可能使部分剩余额度分散，不能宣称任何大小订单都能一次购买。256片若机械沿用每片4 KAS押金，单押金就需1024 KAS，另有C/初始化/结算费用；这些是需要重算的经济设计，不能把旧单轮4 KAS直接当新大轮总押金。

## 4. Schema与数据可用性

以下为逻辑字段，字节编码、上下限与script资源尚未冻结：

- C immutable：版本/网络域、规则承诺、创建者、M、片容量/票额分配、票价、最低开奖票数、允许开始封盘/整体超时规则、全局费用/赏金政策。
- C mutable：phase、初始化/激活进度、sealedBitmap、每片最终count/sold/ledgerDigest/票款摘要、totalSold、winner、paidBitmap/refundActivatedBitmap、储备余额。
- S immutable：轮次谱系/role/index、同一规则承诺、片额度、合法C验证条件。
- S mutable：phase、sold/purchaseCount、完整局部directory、refundCursor；本金/押金从真实输入值核验，不能仅信ledger中的余额。

C只存每片摘要，不存所有购买目录。初版研究有界摘要数组＋位图，避免一开始就依赖复杂Merkle-sum更新；若尺寸超限再评估承诺结构。普通Merkle成员证明不自动证明总票数/前缀和。

权益字段属于Consensus；Indexer's路由/总览为Derived；浏览器偏好和报价租约为Cached；RPC/Indexer地址为External。缺少部分片数据时展示“同步中/已核对部分”，不得按零片计算总奖池。

必须保存并可提供C/S状态前像、片名册和各片完整目录；P2SH本身只承诺脚本哈希，不能认为任意节点都永久提供全部前像。只有hash没有可获得数据会阻断封盘、证明或退款；数据备份/重放/裁剪恢复仍是资金退出前提。

## 5. 购票路由与安全重试

```text
用户：购买本轮q票
  → 路由器读取合法片的容量/状态候选
  → 从多个有余量的片中随机化选择低冲突候选
  → 复验所选片的identity/template/current tip/acceptance及金额
  → 构建 S_i + buyer funds → S_i' + buyer change
  → 明确批准、签名、广播、逐笔接受跟踪
```

BUY不消费C，也不声称读取未消费C的当前phase。合约依赖片内固定规则与本地OPEN阶段，新增票款和购买记录必须原子一致。片内仍顺序更新，跨片互不依赖。

- 不让所有浏览器都选“第一空闲片”，可用随机候选/在途负载分散。Indexer建议不授予共识锁，短期预约不控制资金或形成排他授权。
- 签名前tip变化可以重新准备；签后变更片/outpoint/费用必须重新批准签名。不得修改已签交易。
- 提交状态UNKNOWN时保留资金输入占用及原意图，不跨片生成另一笔同订单购买。原字节重发仍受既有明确边界控制；不存在TTL自动取消。
- 同钱包跨片操作仍可能争用钱包资金输入；输入占用须按网络/钱包统一管理，不能每片各锁各的。
- 接受证明绑定具体片/记录；重组时回滚票权和聚合显示，不把mempool或区块包含作为购票成功。

## 6. 封盘：交易实际冻结，不能用UI截止代替

```text
C_SALES → C_COLLECT
C_COLLECT + S_i_OPEN → C_COLLECT' + S_i_FROZEN
所有名册片恰好登记一次（包括0票片）→ C_READY
```

每笔REGISTER_SEAL核对实际片输入的身份/模板/目录、票款、未登记标志及完整后继。C摘要由真实输入导出；Sn的后继无BUY路径。登记顺序可任意，随机区间顺序必须按预定index，不能让登记者调序。

如果BUY和REGISTER_SEAL竞争同一片输入，只能一个作为有效消费被接受：BUY先成功则重新读取新片后冻结，并把新购买计入；冻结先成功则旧BUY失败并按真实回执处理。不得在后台删除已接受的票。

**关键限制**：C进入COLLECT、页面关闭购买按钮，都不能让未冻结的Sn在共识层瞬间停售。尚未消费片仍可能有合法BUY，必须承认其票权。固定版本CLTV/CSV是成熟下限，不是统一到期上限。第一版候选把此阶段显示为“封盘中”，定义截止为各片冻结完成的结果；若产品要求一个绝对时刻之后所有片都拒绝BUY，当前方案未满足，必须另行证明时间/授权模型，不得写成已实现。

全量冻结后才生成一次C_READY，绑定实际最终票权。C_READY不能任意自续接刷新锚点，也不能删除某片后重抽。空片不能被遗漏，缺片不能由Indexer补零；需要整体超时REFUND出口。

单片登记一笔时，M=256最多需256次C更新，而非65536次BUY更新；它仍是串行协调。固定每步等待10秒的假设下约42分40秒，另有创建/结果下发耗时；不宣称实测TPS或无等待。批处理/树形汇总为后续候选，未验证不承诺。

## 7. 全轮开奖

C_READY保存每片最终有效票数t_i、固定顺序和目录承诺；T=sum(t_i)。最低开奖票数按全轮T判断，各片不自行判定“票少就退款”。

- 从全量冻结后的C_READY输入取得经共识约束的锚点，按新的轮次域绑定固定随机证明/抽样策略。
- 在[0,T)选一个全局票号w；p_i=sum(j<i)t_j，找到p_i≤w<p_i+t_i，片内票号=w-p_i。
- 提供该片被冻结的目录前像（或未来经验证的证明），核对其digest、局部票号区间和买家公钥，得到唯一赢家W。
- C_READY → C_WIN(W, frozenSummary, progress=0)；此后W、票权摘要和WIN决策不可更改。

不能均匀选片再选票，也不能直接取模替代有界拒绝采样。固定PASS-A方案能否以C锚点复用、全量票数范围、时机选择/矿工偏置/延迟公布及DRAW与超时REFUND竞争须重新审查；“先冻结后取随机”本身不是完整公平性证明。

## 8. 派奖：同一赢家，多笔实际付款

首版候选保持资金在各Sn中，消费实际C_WIN以授权每片支付：

```text
C_WIN(W) + S_i_FROZEN + fee funding
    → C_WIN'(W, paidBitmap加i) + W的奖金份额 + 押金/执行者/找零等明确普通输出
```

C和Sn都校验身份、role、冻结摘要、片未支付、唯一赢家、正确金额与全部输出。S_i终止，不能重复付款；最后一片之后才可释放不再需要的C协调储备/押金。

- 用户看到一个中奖结果，以及“应到账/已到账/待到账”的累计进度。底层多个txid只放可选明细。
- 多笔到账是实际行为，不能把钱包余额未到账部分标记已领取，也不承诺一次签名自动发256笔。
- 付款可由permissionless执行者推进，资金直接付给W，无需W签名授权其收款；若执行者用自己的普通资金付费，他仍须签名，用户钱包不会被静默调用。
- 奖金分摊、每片执行费、创建押金退还与C储备守恒必须冻结。全轮赏金不能直接复制成每片各1 KAS；用户应看到预计净奖金而非把押金/运维储备计入奖池。
- 这个版本派奖仍经C串行，但操作量按M计算。把结果通过不可伪造凭证并行下发是后续优化，本版不假定已有该证明。

## 9. 统一退款决策，局部并行执行

```text
C_COLLECT/C_READY（满足已定义退款条件）→ C_REFUND
C_REFUND + S_i_OPEN/FROZEN → C_REFUND' + S_i_REFUNDING
S_i_REFUNDING → 本片下一批退款或终止       // 无需C
```

C_REFUND一旦生效不能转回WIN。C_WIN一旦生效也不得转REFUND；部分奖金已支付后，剩余片只能继续向同一赢家付款，不能各自超时退款。双方竞争必须消费同一个控制谱系输入，客户端按当前selected-chain接受状态处理重组。

对未完成封盘的片，退款激活须消费该片实际最新状态，保留所有真实购买；不能用旧摘要跳过后来成功的BUY。激活标志防止重复，片的REFUNDING不可恢复OPEN/付款WIN路径。各片按本片记录推进游标，保持最多32条批次的候选边界。

C分发完所有退款状态不等于所有买家已收款。UI按片退款交易的接受进度聚合为同一轮“退款中”；全部退出后才显示已结束。若用户有多条/多片记录，以“已退/待退金额”聚合，不能承诺点击一个按钮就能绕过其他前置记录直接领取。

**异常退出仍BLOCKED**：初始化部分完成、数据丢失、C无人推进、冻结长期受BUY竞争、退款激活不完整、网络费超限、执行者无利可图及中奖模式后最后几片无人付费等，须有权限开放、资金来源明确、资源可行的恢复路径。不能依靠运营者一直在线来伪装无条件可退出。

## 13. 8项anti-pattern

| 项 | 本草案结论 |
|---|---|
|1 全局状态管全部用户|C不参与BUY；协调阶段共享仅为全轮完整冻结/唯一结果，仍须测资源。|
|2 只验签不验后继|第10节要求完整角色后继与资金校验，未实现，不能称安全通过。|
|3 同CID即信状态|同family仅身份候选，必须验证模板、role、唯一发行和状态机，BLOCKED。|
|4 Indexer裁定资金|聚合数为展示，冻结/结果/付款以脚本与节点接受核验；缺片不伪完整。|
|5 Solidity式远程读取|S不读取未消费C；统一结果通过实际共同输入传递。|
|6 为方便全操作共享UTXO|BUY不写C；路由服务不创造新的全局排他授权。|
|7 无退出|初始化/缺数据/无激励退出尚未闭合，明确阻断；不许靠关闭UI掩盖。|
|8 只验bytes不验模板谱系|所有跨role输入/输出须对模板、身份、状态和value完整核验。|
