# Kaspa covenant 能做什么：一个不用托管的抽奖

> 本文以 Kaswin V2.0.2 为例，讲清楚 Kaspa covenant 在实际项目里能承担哪些职责、哪些必须放在链下，以及一个不用托管的抽奖是如何只用三个合约模板跑起来的。
>
> 合约源码固定为 `kaspanet/silverscript` 提交 `3ed973335b59269293564805cc2c58a14595ec03`，共识参考固定为 `kaspanet/rusty-kaspa` 提交 `cfafeb4c093fa37a303f1b9f19c58f986b870ce3`。文中参数均取自该版本合约源码，不是对任意节点兼容性的声明。

## 先说结论

covenant 不是"把智能合约搬到 Kaspa"。它做的事只有一件：

**给一个 UTXO 绑定一个身份，然后规定这笔钱下一次只能被什么样的交易花掉。**

听起来很窄，但足够撑起一类完整的应用——只要你能把应用状态塞进一个 UTXO 的脚本里，并且把状态转移规则写进这个脚本，你就得到了一个没人能单方面改写规则的链上应用。

抽奖刚好是这类应用里最好的例子：规则简单、资金敏感、结果必须公开可验证，而且运营方天然有作弊动机。下面用它把 covenant 的能力边界摊开。

## 一、为什么"不用托管"在抽奖里是真需求

传统链上抽奖的做法，钱打到运营方地址，开奖时运营方调接口摇号。哪怕代码开源，用户也只能信任三件事：运营方真的用了他声称的随机源、开奖时奖池里的钱还在、运营方不会跑路。

这个信任模型的问题不在于运营方一定作恶，而在于**用户没有办法验证，只能相信**。一旦出事，事后也无法证明。

用 covenant 改造后，这三件事变成链上可查：

| 传统做法 | covenant 做法 |
|---|---|
| 钱在运营方地址 | 钱在一个绑定轮次身份的 UTXO 里，脚本规定只有符合规则的花法 |
| 运营方摇号 | 开奖结果由封存之后第一个跨过边界的链区块头决定，任何人可复算 |
| 规则写在后台 | 规则写死在合约脚本里，改规则等于换一个合约、换一个轮次身份 |

关键在于最后一行：**运营方想改规则，做不到悄悄改**。改了就是另一个合约，用户能看出来。

## 二、Kaspa covenant 的三个实际能力

把抽奖拆开看，需要三件事：身份、状态、可验证随机性。covenant 在前两件上是直接给答案，第三件只给一半。

### 1. 身份：covenant ID

Kaspa 的 covenant 用 `covenantId` 标识一个合约谱系。这个 ID 在合约创建时由创建输入和创建输出算出，之后沿着这条谱系一直传递下去。

在 Kaswin 里，轮次身份（CID）这样定义：

```text
CID = covenantId(origin, [{index: 0, value: DEPOSIT, spk: p2sh(blake2b256(genesisScript))}])
```

`origin` 是创建这笔资金的普通 UTXO，`genesisScript` 是初始 OPEN 状态的合约脚本。

这带来一个很强的性质：**CID 同时绑定了资金来源和初始规则**。同一个 CID 不可能对应两套规则，也不可能凭空造出来。所以"这是第几号轮次、它的规则是什么"不需要运营方声明，用户可以自己从链上算出来。

这也是后面所有核验的锚点——客户端不信任索引器给的任何字段，只信"这个 UTXO 的 CID 是不是我要的那个，它的脚本是不是能把账本哈希出来"。

### 2. 状态：把账本塞进脚本

这是 covenant 最反直觉的部分，也是它真正的门槛。

EVM 里状态存在合约存储里，随交易更新。UTXO 模型没有存储。所以想表达"售票进行到第 37 张、卖了 5 张"，只能把状态本身编码进下一笔 UTXO 的脚本里。

Kaswin 的账本是一个固定布局的字节数组，叫 KW21：

```text
80 字节头 + 每条购买记录 36 字节，最多 256 条

头里包含：magic、阶段、票价、票数上限、购买记录上限、
          最少票数、可封盘 DAA、已售票数、购买记录数、
          退款游标、owner 公钥
每条记录：4 字节累计票号 + 32 字节买家公钥
```

每次买票，合约做的事是：

1. 校验输入脚本的 P2SH 等于当前账本编码出的合约脚本；
2. 把账本拷出来，追加一条记录，票数加一；
3. 校验新输出的脚本等于**新账本**编码出的合约脚本，金额等于新账本算出的锁定金额；
4. 校验 CID 不变，且输入 0 是唯一的合约输出。

第 3 步是核心。合约不"保存"状态，它**要求下一笔交易的输出必须承诺新状态**。状态不在任何地方存着，它就是那个 UTXO 的脚本本身。

代价也很直接：

- **状态大小受限**。256 条记录是写死的上限，不是随便设的——账本越长，脚本越大，交易 mass 越高。
- **每次操作都要重算整个脚本**。买第 200 张票和买第 1 张票的链上成本不是一个量级。
- **不能有并发**。同一轮只有一个状态 UTXO，两个人同时买，后一笔会因为输入已被花掉而失败，必须重试。

这些不是缺陷，是 UTXO 模型下表达可变状态必须付的代价。设计应用时要先接受它，再决定状态怎么切。

### 3. 随机性：covenant 只给一半

这是最容易被讲错的地方，值得单独一节。

**合约本身产生不了随机数。** 链上没有熵源，脚本里能读到的都是确定值——输入、输出、金额、DAA 分数。谁想用脚本里的"哈希一下"造随机数，都是在自欺欺人：这些值在构造交易时就已知，可以提前挑。

所以随机性必须来自合约控制不了的东西。Kaswin 用的是**未来的链区块头**：

```text
边界 DAA = 封存状态 UTXO 的 DAA + 100
开奖种子 = blake2b("KASWIN_V2_DRAW" || CID || 封存 outpoint || 冻结账本 ||
                  边界 DAA || 目标区块哈希 || 目标区块的序列承诺)
```

目标区块是**封存之后第一个跨过边界 DAA 的链区块**。合约在开奖时校验：

- 父区块 DAA < 边界 ≤ 目标区块 DAA（第一个跨过边界）；
- 目标区块的 `acceptedIdMerkleRoot` 等于脚本算出的序列承诺；
- 目标区块哈希确实是交易声明的那个。

因为封存时目标区块还不存在，运营方没法挑。等目标区块出来，种子就固定了，任何人可以复算。

**但这里有个必须说清楚的限制**：这段证明（PASS-A，240 字节）需要从节点读取两个区块头加上一条 lane proof。它不是合约自己产出的，是客户端组装、合约校验的。所以合约保证的是"如果你给我的证明符合这些条件，种子就是唯一确定的"，而不是"合约能自己去取随机数"。

这也意味着，开奖交易的提交者必须能读到目标区块。Kaswin 在客户端要求这个目标达到 100 blue score 的确认深度才允许开奖——这是客户端策略，不是共识规则。合约只认 DAA 边界，不认确认深度。

这两者不能混为一谈。合约说"可以开奖了"，和客户端说"我确认这个区块稳了"，是两个独立判断。

## 三、三个模板，一条状态机

Kaswin 的合约不是一个大合约，而是三个固定模板：

```text
普通资金 → GENESIS → OPEN
OPEN  → BUY            → OPEN
OPEN  → CLOSE          → SEALED / REFUNDING / EMPTY
SEALED → DRAW_AND_PAY  → PAID
SEALED → TIMEOUT_REFUND→ REFUNDING
REFUNDING → REFUND     → REFUNDING / REFUNDED
```

- **OPEN**：售票。重算 Genesis CID，硬编码指向 SEALED 和 REFUNDING 的模板哈希。
- **SEALED**：等待开奖或超时退款。带 PASS-A 校验和种子推导。
- **REFUNDING**：逐批退款，推进游标，最后一批把押金也退掉。

拆成三个模板而不是一个，是为了控制单笔交易的脚本规模。每个模板只带自己需要的逻辑，转发时校验下一阶段的模板哈希。

这也是 covenant 编程和普通智能合约在工程上的差别：**合约不是被"调用"的，是被"接力"的**。每一笔交易都是把状态交给下一个模板，交接的合法性由当前模板校验。

## 四、资金守恒是怎么保证的

抽奖最容易出问题的地方是钱。Kaswin 的约束写在合约里：

**买票**：输入金额必须等于 `DEPOSIT + 已售票数 × 票价`，输出金额必须等于 `DEPOSIT + 新售票数 × 票价`。差额正好是票价，没有中间地带。

**开奖**：输入只有一个，输出必须恰好三个——

```text
奖金   = 票价 × 已售票数 - FINALIZER - 执行费
押金   → owner
执行费 → 执行者
```

`FINALIZER` 是固定值（1 KAS），不是百分比。也就是说**奖金金额在封盘那一刻就已经确定了**，运营方在开奖时没有任何调节空间。

**退款**：每批推进游标，每条的退款额是票价，执行费按记录数计，最后一批额外扣一次固定费把押金退掉。全程账本保留，只动游标。

**超时**：封存输入的实际 DAA 达到 `utxoDaa + 432000` 后，任何人都能把轮次转到退款。运营方不开奖，钱不会锁死——这是整个设计里最重要的一条退出保证。

注意 `432000` 这个数字：它不是"12 小时"，是 DAA 分数。Kaspa 的 DAA 分数和墙钟时间不是线性对应关系，直接换算成时间会算错。这也是很多类似项目踩过的坑。

## 五、链上做了什么，链下必须做什么

一个常见的误解是"合约能保证一切"。实际上 Kaswin 的合约只管资金和状态转移，下面这些全在链下：

| 职责 | 在哪 | 为什么不能在链上 |
|---|---|---|
| 发现轮次 | 索引器 | 合约不知道有哪些轮次存在 |
| 读当前状态 | 节点 UTXO | 状态就是 UTXO，但要知道查哪个地址 |
| 组装开奖证明 | 客户端 | 合约无法主动读取区块 |
| 判断"已接受" | 节点 | 区块包含 ≠ 交易接受 |
| 重组后恢复 | 客户端 | 合约只看当前状态，没有记忆 |

第二行值得展开。因为状态就是 UTXO，"当前状态是什么"这个问题等价于"这个 CID 在节点 UTXO 集里的那笔输出是什么"。客户端拿到一个候选账本后，会自己算出合约地址，去节点查这个地址上的 UTXO，然后验证：

- UTXO 的脚本等于 `P2SH(账本编码出的合约脚本)`；
- UTXO 的 CID 等于轮次 CID；
- UTXO 金额等于账本算出的锁定金额；
- 脚本里的 origin 能推出这个 CID。

四条全过，这个账本就是当前状态。**索引器说什么不重要，它只是告诉你去看哪个地址。**

第五行是实际运营中最容易出事故的地方。短程重组会把已经看到的接受块换掉，客户端必须能识别并重新核验。Kaswin 里这块代码量比合约本身还大——这不是过度设计，是 UTXO 链上做应用的必需品。

## 六、这套东西适合做什么，不适合做什么

**适合**：

- 规则固定、资金敏感、结果需要公开可验证的场景：抽奖、拍卖、托管、质押、投票计票。
- 参与人数有限、状态能塞进一个 UTXO 的场景（Kaswin 的上限是 256 条记录）。
- 需要"运营方也无法作弊"作为卖点的产品。

**不适合**：

- 需要高频写入或高并发的场景。单一状态 UTXO 就是天然串行。
- 状态很大的场景。账本越大，脚本越大，成本非线性上升。
- 需要复杂计算或循环的场景。脚本有执行预算，不是图灵完备的通用环境。
- 需要"合约主动触发"的场景。合约不会自己动，必须有人构造交易。

第三条经常被低估。EVM 开发者习惯了"合约里写个循环处理 1000 条记录"，在 covenant 里这会让脚本膨胀到无法提交。

## 七、踩过的坑

写下来给同样在做的人，省点时间：

**1. 区块包含不等于交易接受**

Kaspa 的交易被区块包含之后，还可能在虚拟链重排中被移出。判断"这笔交易真的被接受了"必须读节点的接受数据，不能只看浏览器说"有这笔交易"。这个区别在别的链上不那么明显，在 Kaspa 上会直接导致误判。

**2. 索引器只能是发现层**

索引器挂了、落后了、数据错了，都不能影响资金安全。所以客户端所有关键判断都必须回到节点重算。Kaswin 的索引器只做两件事：告诉你有哪些轮次、给你一个候选账本——后者还要被完整核验。

**3. 历史会被裁剪**

节点只保留有限时间的区块数据。轮次存活时间一长，接受块就被裁掉了，读不到完整交易。这时候如果客户端坚持"必须先读完整交易"，整个轮次就无法操作了。

解决办法是回到"状态就是 UTXO"这个本质：只要 UTXO 还在、且它的 DAA 低于节点的裁剪点，就说明它的接受早于裁剪点、已经不可能被重组，这时可以只凭 UTXO 完成核验，不需要完整交易。代价是丢失了接受块位置信息——但那正是此时不再需要的东西。

**4. DAA 分数不是时间**

前面提过，但值得重复。所有涉及超时、等待、边界的判断都要用 DAA 分数，不要换算成秒。

**5. 重发和加速要区分"已提交"和"已被替换"**

同一笔操作可能因为费用不足被替换交易取代。旧交易被替换后，它的输入占用必须释放，否则会永久阻塞后续操作。这类状态机细节比合约逻辑更容易出 bug。

## 八、已经跑在链上的东西

前面讲的都是设计。这一节放真实记录，因为"能自证"是这套东西唯一的卖点。

### 主网：两个各 500 张票的进行中轮次

主网当前有两个售票中的轮次，各已售出 500 张票，票价 1 KAS：

| CID | 已售 | 锁定金额 | 状态 |
|---|---|---|---|
| `183de5b55e0178ba…` | 500 张 | 504 KAS | 售票中 |
| `7e48d62abbc9d164…` | 500 张 | 504 KAS | 售票中 |

锁定金额 504 KAS = 押金 4 KAS + 500 张 × 1 KAS。这个数字由合约算出来，不是运营方填的。

这两个轮次用的都是 1 KAS 票价的真实资金。

### 主网：一个已开奖的轮次

轮次 CID `31e2aaca3fc9c393…`，11 张票，票价 1 KAS，状态 PAID。

创建交易：`b366fbf8918c719c…`
开奖交易：`1502291409a92e5a…`

开奖交易的三个输出，对照第四节公式：

| 输出 | 金额（sompi） | 对应 |
|---|---|---|
| 0 | 999,090,200 | 奖金 |
| 1 | 400,000,000 | 押金退回 owner |
| 2 | 100,000,000 | FINALIZER 给执行者 |

验算（1 KAS = 100,000,000 sompi，票价 100,000,000 sompi = 1 KAS）：

```text
票款       = 100,000,000 × 11      = 1,100,000,000
奖金       = 1,100,000,000 − 100,000,000 − 909,800 = 999,090,200  ✓ 输出 0
输入       = 400,000,000 + 1,100,000,000 = 1,500,000,000
输出合计   = 999,090,200 + 400,000,000 + 100,000,000 = 1,499,090,200
手续费     = 1,500,000,000 − 1,499,090,200 = 909,800
```

三项都对得上，分文不差。

这两个交易可以在任何 Kaspa 主网浏览器上查。**这就是"规则写死在合约里"的实际含义**——奖金金额不需要谁公布，你自己按公式算一遍就能核对。

要说明一点：这个轮次的 owner、中奖者和执行者用同一个公钥（三个输出收款脚本相同），是运营方自测轮次。它的证据价值在于**金额和状态转移符合合约公式**，不在于"有第三方中奖"。

### 浏览器自动化测试：每个分支都跑过

`tests/output/` 下保留了完整的自动化测试运行记录，每个场景一次真实链上运行：

| 场景 | 结果 | 耗时 |
|---|---|---|
| empty | ✅ EMPTY | 61s |
| refund-2ticket | ✅ REFUNDED | 78s |
| payout | ✅ PAID | 94s |
| A4 | ✅ PAID | 77s |
| concurrent-race | ✅ PAID | 195s |
| R225 | ✅ REFUNDED | 2103s |
| P256 | ✅ PAID | 12s |
| R256 | ✅ REFUNDED | 86s |
| empty（复跑） | ✅ EMPTY | 76s |

覆盖的内容值得单独说：

- **empty**：无人购票，押金退回；
- **payout / A4**：正常开奖派奖；
- **refund-2ticket / R225 / R256**：退款，其中 R225 跑了 2103 秒——那是 225 条记录分批退款，验证了游标推进；
- **P256**：256 张票，正好撞上购买记录上限；
- **R256**：256 条记录全部退款；
- **concurrent-race**：并发竞争，验证单一状态 UTXO 下后到的交易被正确拒绝。

这些不是 mock，是浏览器驱动的真实链上交易，每条的终局状态和 txid 都记录在 `tests/output/runs/*/summary.md` 里。P256 和 R256 两个场景尤其有价值——它们把 256 条记录的边界条件真实跑了一遍，而这正是账本塞进脚本时最容易崩的地方。

### 当前形态

- 单个 HTML 文件，浏览器直接打开，不需要插件或 WASM SDK；
- 支持 Testnet 10 和主网，构建时决定哪个网络可交易；
- 合约 V2.0.2，Profile `ed0387c9e77bb4e0a8f1f4654a326c316d83663f455283ec6a046a095c94856d`；
- 源码在 [github.com/agang0311/kaswin](https://github.com/agang0311/kaswin)。

### 还没做到的

合约有固定的编译产物，TN10 上每个终局分支都用浏览器自动化测试真实跑过。但下面这些**没有完成**：

- 没有第三方审计；
- 没有长期运行验证；
- 主网只有小额自测轮次（目前两个售票中各 500 张 1 KAS 票的轮次，一个已开奖的 11 张票轮次）。

所以这篇文章描述的是设计和已实现并观察到的行为，不等于"可以放心投入大量资金"。这个圈子里，把"已实现"说成"已验证"是最常见的失信方式，与其事后解释，不如一开始就分清。

## 结语

回到标题的问题：Kaspa covenant 能做什么？

它能做的是**把规则的所有权从运营方手里拿走，交给一个所有人都能检查的地方**。它做不到的是让应用变简单——相反，把状态塞进脚本、处理重组、区分接受和包含，这些都比在 EVM 上写同样的逻辑更麻烦。

所以它适合的场景很明确：当"运营方无法作弊"这件事本身值钱，值得为它付出这些复杂度时。

抽奖就是这样一个场景。不是因为抽奖需要复杂的技术，而是因为抽奖最需要的恰恰是"你不用相信我"。
