## 2026-11-14 extension: multi-shard payout and refund

Only two rounds are added, one writer at a time:

- `multi-payout`: 513 buys (512 x 1 ticket + a final 3-ticket buy) = 515 tickets, two frozen shards plus a tail pool of 3 TKAS (= `TAIL_POOL_MIN`), so the expected finish is PAY_OLD (k=2) then PAY_SELF.

- New cumulative bounds across all `artifacts/tn10` runs: at most 1550 tickets (520 already used + 2 x 515) and cumulative network fees at most 60 TKAS. These are execution limits, not a forecast of spending. Stop before exceeding them.

The Testnet 10 page, node proxy and budget service on this host are test-only; the delivered artifact is the web page, and the services it uses are deployed separately.
- **Concurrency (2026-11-14, user request)**: the two new rounds run at the same time, which is within the existing "3 simultaneous rounds" bound. To keep them from selecting the same funding UTXO they use disjoint dedicated wallets: `--lane=A` = creator + buyer1 (every buyer2 buy is routed to buyer1), `--lane=B` = buyer2 for every role (creator and buyers of that round are the same wallet). Each lane has its own writer lock (`writer-A.lock`, `writer-B.lock`); lane locks and the legacy `writer.lock` exclude each other. `multi-payout` started before lanes existed (its first buys alternated buyer1/buyer2) and was resumed as lane A from its original state; `multi-refund` runs as lane B. No other wallet, key or limit changes.
- **Acceptance pacing (2026-11-14, user correction)**: the first six rounds waited for 100 DAA depth before every next transaction. That is not the V2.0.2 flow. From the two multi-shard rounds on, the runner follows V2.0.2: the first selected-chain acceptance is a CANDIDATE and the next transaction may be prepared and sent immediately (zero-depth chaining). A candidate becomes ACCEPTED only after a re-check with its accepting block at least 100 DAA below the virtual DAA, still on the selected chain, matching the approved draft and with an unchanged accepting DAA (`finalizePending`, run every loop iteration and awaited before a round is reported complete). A failed re-check stops the run (fail closed). Receipts carry `candidate`/`accepted`/`finalized`; a round is complete only when every receipt is ACCEPTED. A reorg deeper than the unfinalized tail would invalidate chained descendants; that is the accepted cost of V2.0.2-style chaining and would be reported, not hidden.
- **Re-acceptance after a shallow reorg (observed 2026-11-14)**: with zero-depth chaining, a tip reorg on Testnet 10 displaced the accepting block of the newest candidate in both concurrent rounds at once; the same signed bytes were accepted again in another chain block at a DAA 1-3 higher or lower. The runner therefore re-finds the acceptance from the intent cursor, re-checks it against the approved draft, keeps the old location in `reaccepted`, refreshes the DAA of the UTXOs that transaction created, and keeps the receipt a candidate until the >=100 DAA re-check passes. Input UTXO DAA drift no longer fails the live-input check (value, script and covenant id are still compared). A candidate that is neither accepted nor in the mempool (for 3 minutes) stops the run (`CANDIDATE_DROPPED`). Next-step preparation also retries `STALE_INPUT` for up to 40 x 0.5 s, and an unsent intent that failed that check is archived and rebuilt, never replaced after submission.
- **Web page (2026-11-14, user request)**: the standalone page follows the same V2.0.2 pacing as the runner (first selected-chain acceptance is a candidate and the next step may be prepared at once; ACCEPTED only after the >=100 DAA re-check; a moved accepting block is re-found; a lost candidate halts the round). No new on-chain run was made with the page.
