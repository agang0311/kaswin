## 4. 子代理静态审查结论（gpt-6.1-sol，**源码推演、未实测**）

- 按钮启用条件依赖**本地** round state（`round.mjs:44-65`），不校验余额、分片与 UTXO 实时存活；过期一般报 `STALE_INPUT`。
- 空闲自动刷新每 8 秒一次，仅 busy/弹窗暂停，并保存/恢复焦点——**不存在**「输入框聚焦导致时间锁到期按钮不亮」的问题。
- 高：`PREPARED` 意图落盘后断页且输入被他人花掉 → 不能重发、不能放弃，常规 UI 无出口（`intent.mjs:98`、`controller.mjs:161,187`）。
- 高：带未完成意图长期离线，游标落后超过搜索范围 → 刷新/重发/放弃都卡在 `SEARCH_RANGE`（`chain.mjs:93`）。
- 中：零余额私钥钱包点 REFUND_SELF 会被要求选资金并报余额不足；改用「仅收款地址」可绕过（`prepare.mjs:99,112`）。
- 导入侧：`pending[].intent` 缺完整结构校验（只验顶层 intent），可让所有轮次的准备交易抛错；收据 `feeSompi` 未校验，错误值会让详情页渲染抛错；同 CID 文件导入后旧的「已核对」绿标未清除。
- 私钥只存在钱包闭包；导出会带出 intent/pending 内的 `signatureScript`、proof/accessor，但**未发现**读取内存私钥的导出路径；未发现导入数据绕过 HTML 转义读取私钥的路径。

## 7. 对子代理静态结论的源码核对（2026-11-14）

子代理（gpt-6.1-sol）的静态报告标注「源码推演、未实测」。以下逐条核对源码后的判定。

### 7.1 按钮条件表：成立

`round.mjs:42-66` 与报告一致：

| 阶段 | 条件 |
|---|---|
| sales | `BUY: N<256 && T<cap`；`CLOSE` 在 `T<cap && N<256 && currentDaa<closeEligibleDaa` 时禁用 |
| sealed | `DRAW` 需 `currentDaa>=utxoDaa+100` 且 `< utxoDaa+TIMEOUT_DELAY-1000`；`TIMEOUT` 需 `>= utxoDaa+TIMEOUT_DELAY` |
| win | `PAY_OLD: p<N`；`PAY_SELF: p===N && local>0 && !mergeTail` |
| refund | `REFUND_OLD: r<N`；`REFUND_SELF: r===N && records非空 && !mergeTail` |

`gate()`（`app.ts:61-70`）只检查本地存储、节点、服务、钱包类型与 busy，**不检查余额**；`availableActions` 只用本地 state 与 DAA。
所以「亮灯 ≠ 链上一定可执行」成立，但过期一般会以 `STALE_INPUT` 显式失败，不是静默成功。

### 7.2 结论①（PREPARED 意图无出口）：成立，但条件比报告更窄

- `intent.mjs:2`：状态机为 `PREPARED → SUBMITTED | UNKNOWN | REJECTED | UNSENT`。
- `controller.mjs:161`：`discard` 只接受 `REJECTED/UNSENT`（`settled`）或 `SUBMITTED/UNKNOWN`，**`PREPARED` 会抛 `DISCARD_NOT_ALLOWED`**。
- `round.mjs:47`：只要 `round.intent` 存在，八个动作全部禁用。
- `controller.mjs:187`：导入新状态时若本地有 intent，要求 wireDigest 相同，否则 `IMPORT_WOULD_REPLACE_LOCAL_INTENT`。

关键修正：**存在一条正常出口**。`track(recover:true)`（「重新发送」）会对 PREPARED 意图重发同一份签名交易，成功后状态变 `SUBMITTED`，随后「放弃」可用。
只有当**输入已被他人花掉**时，重发抛 `STALE_INPUT` → `conflict=true`、状态不变 → 才真正进入死局（既不能重发、不能放弃、也不能导入新状态）。
所以这是真实死锁，但触发窗口很窄：页面必须在「意图已落盘」与「发起提交」之间崩溃/关闭，且该输入随后被他人花费。

### 7.3 结论②（SEARCH_RANGE）：成立

- `scripts/chain/chain.mjs:93`：`ensure(sink - start.header.blueScore <= sinkLagLimit, …, 'SEARCH_RANGE')`，默认 `sinkLagLimit = 400_000n`。
- `intent.mjs:91`：`checkAcceptance` 只把 `NOT_CHAIN/REORG/CURSOR_REORG/NOT_ACCEPTED/SINK_BEHIND/RPC_TIMEOUT/READ_VIEW_CHANGED` 当可重试，**`SEARCH_RANGE` 会直接抛出**。
- `controller.mjs:167`：`discard` 要求 `checkAcceptance` 返回 `complete===true`，抛错即失败。

TN10 约 10 blue score/秒，400,000 约等于 **11 小时**。带未完成意图离线超过这个时长后，「刷新/重新发送/放弃」三条路都会失败，UI 无出口。与「超时转退款 12 小时」同一量级，实际会遇到。

### 7.4 结论③（零余额私钥钱包无法 REFUND_SELF）：成立

`prepare.mjs:99`：`const needsFunds = FUNDED.includes(action) || (action==='REFUND_SELF' && keyed);`
`prepare.mjs:100`：`check(!needsFunds || keyed, 'WALLET_KEY_REQUIRED')`。

即：用**私钥**钱包做 REFUND_SELF 会强制走 `selectFunds`（门槛 `FEE_CAP+1`，约 0.5 TKAS），余额不足就报错；改用「仅收款地址」则 `needsFunds=false`，不需要任何资金。
这与页面文案「派奖与退款只需要一个收款地址」不一致，属于可绕过的低效设计，不是阻断。

### 7.5 被纠正的旧认识

先前依据 `TN10-DEPLOYMENT.md` 里「自动刷新在输入框聚焦时跳过」的描述，怀疑时间锁到期后按钮不亮。**当前源码并非如此**：
`app.ts:318` 每 8 秒刷新，`render()` 前后 `captureFocus/restoreFocus`（`app.ts:77,91,95`），没有基于聚焦的跳过。
本次实链测试也印证：封盘与开奖按钮到点后都正常点亮。

### 7.6 判定汇总

| 子代理结论 | 判定 |
|---|---|
| 按钮条件表、亮灯不校验余额 | 源码成立 |
| ① PREPARED + 输入被花 → 无出口 | 源码成立；比报告窄（正常有「重新发送」出口） |
| ② 离线超 ~11h → SEARCH_RANGE 死锁 | 源码成立，实际会遇到 |
| ③ 零余额私钥钱包 REFUND_SELF 被拦 | 源码成立，可用仅收款地址绕过 |
| 无「聚焦导致按钮不亮」 | 成立，并纠正了我先前的错误假设 |
| 缺分片时导入先报 ROUND_FROZEN_COUNT/PREIMAGE | 与 `round.mjs:169-173` 一致 |

以上均为源码核对，**未构造死锁复现**；本轮实链测试没有触发这些状态。

## 8. 导入/渲染面静态结论的实测（2026-11-14）

方法：用页面自身的「导出」拿到真实 round state（`kaswin-rolling-<cid>.json`，8,696 字节，1 条 receipt、无 pending），
用 `#sFile` 文件导入注入变异版本，观察 toast 与 `pageerror`。全程未签名、未广播。

### 8.1 V1：`pending[].intent` 结构未校验 —— 实测成立，且比静态报告更严重

变异：`pending:[{txid, acceptingBlock, acceptingDaa, intent:{txid}}]` + 一条 `finalized:false` 的同 txid receipt。
`validateRound`（`round.mjs:151-153`）只校验 `p.intent.txid===p.txid` 与 receipt 存在，不校验 intent 内部结构。

结果：**导入被接受**（toast「已导入 1 个轮次」），随后
- `BUY` 按钮变为不可用；
- 页面抛 **`TypeError: Cannot convert undefined to a BigInt`**（连续 3 次 `pageerror`）。

即不是静态报告说的「准备交易抛错」那么温和，而是渲染/判定阶段直接抛类型错误。重新导入原始导出即恢复正常。

### 8.2 V2：`receipts[].feeSompi` 未校验 —— 实测成立

变异：`receipts[0].feeSompi = "x"`。`round.mjs:148` 只校验 `txid` 与 `action` 类型。

结果：**导入被接受**，渲染时抛 **`SyntaxError: Cannot convert x to a BigInt`**（2 次 `pageerror`）。

### 8.3 V3：同 CID 覆盖导入不清除「已核对」—— 实测成立

步骤：先点「向节点核对」得到绿标「已向节点核对（…）：本机记录与链上状态一致。」，
再导入同 CID、`manager.outpoint.transactionId = ff…ff / index = 7` 的伪造状态。

结果：导入被接受，**旧绿标仍然显示**。核对结论没有被新状态失效（`app.ts:128,220`）。
这属于信任信号问题：用户可能把「未核对的伪造状态」当成已核对。

### 8.4 正面结论

- 私钥：三份导出中均未出现私钥；页面未提供读取内存钱包私钥的导出路径。
- 恢复：重新导入原始导出即可完全恢复正常操作（BUY/CLOSE 均恢复可用）。
- 结算：测试用轮次已 `CLOSE`（0 票）→ **空轮结束 EMPTY**，4 TKAS 押金回到创建者（链上 `eaadc46d…` 含 4 TKAS 输出）。

### 8.5 边界

变异只针对 `pending`、`receipts.feeSompi`、`manager.outpoint` 三处；未测试 `frozen` 分片、`indices`、`settings` 与分享链接 base64 路径。
所有注入均为本地导入，不涉及签名或广播；`roundFromText` 的 `source:'imported'` 标记未阻止上述渲染异常。

## 9. 跨标签页与持久化的实测（2026-11-14）

方法：同一 Chromium context 内开两个标签页 A/B（同源、共享 localStorage），A 保存后 B 再保存，读 `localStorage` 与 `data-theme`。

### 9.1 设置丢失更新 —— 实测成立

`app.ts:259` 保存时把两个字段一起写回：
```js
S.nodes = $('sNodes').value.trim() || defaultNode;
S.svc   = $('sSvc').value.trim()   || defaultService;
LS.set('nodes', S.nodes); LS.set('svc', S.svc);
```

复现：A 把节点设为 `wss://vector-10.kaspa.green/…`（顶栏「已连接」）→ B（页面打开较早，面板里仍是默认节点）只改服务地址后保存
→ `localStorage` 的 `nodes` **被改回** `wss://cd311.cn:888/www/rolling-tn10/node`，A 的设置丢失。

影响：多标签页时节点配置会被静默回退；节点地址决定页面连哪个链视图，回退后可能连回旧/不可用端点，而用户不会收到提示。
修法：保存前合并未修改字段，或对同一键做版本/时间戳比较，冲突时提示。

### 9.2 主题不跨标签页同步 —— 实测成立

源码层面 `web/rolling-tn10/` 内**没有任何 `addEventListener('storage')` 或 `BroadcastChannel`**。

复现：A 点主题按钮切到浅色 → A 变 `light`，B 仍 `dark`；B 聚焦、切换页面后仍 `dark`；在 B 上注册 `storage` 监听 2.5 秒内**未收到事件**。
关闭全部标签页重开后主题为 `light` —— 说明持久化本身正常，缺的只是同源多标签的同步。

### 9.3 与本文件其他结论的关系

9.1 的丢失更新与第 8.3 节的「同 CID 覆盖导入不清除已核对」属于同一类问题：**本地偏好与信任状态缺少失效/合并规则**。
切换节点后旧的「已核对」绿标是否失效，本轮**未测**（见第 10 节）。

## 11. 响应式与可访问性的实测（2026-11-14）

方法：Chromium 在 390×844、360×740、1280×900 三档下测量几何尺寸、可聚焦性、对比度（WCAG 相对亮度）。

### 11.1 键盘无法导入轮次文件 —— 实测成立（阻断）

`views.ts:342`：`<label class="btn">导入轮次文件<input id="sFile" type="file" … hidden></label>`。
实测 `#sFile` 为 `NOT-focusable(hidden)`，`label` 的 `tabIndex=-1`。三档视口一致：

## 13. 设置与钱包面板的实测（2026-11-14）

### 13.1 坏节点地址被持久化 —— 实测成立

`app.ts:259` 的 `onApplyConn()` 先写 `localStorage`，再 `connectAuto()`：
```js
S.nodes = $('sNodes').value.trim() || defaultNode;  S.svc = …;
LS.set('nodes', S.nodes); LS.set('svc', S.svc);
await connectAuto();
```
实测填 `wss://` 保存后：`localStorage['kaswin-rolling-tn10:nodes'] === "wss://"`，顶栏「连接失败」，**刷新后仍失败**。
失败原因只写进「高级设置 → 运行日志」，顶栏没有原因。恢复路径存在（改回或清空再保存），未死锁。

### 13.2 钱包错误提示被弹窗遮住 —— 实测成立（比报告更严重）

以 `kaspatest:zzzznotanaddress` 连接，toast 文案「操作没有完成（错误代码 USER）。可在「高级设置」里查看日志。」
在 toast 中心点做 `document.elementFromPoint`，返回 **`dialog#modal.modal`** —— toast 被 `<dialog>` 完全遮住。

原因是 `<dialog>` 处于 top layer，任何页面级 toast 都无法盖在打开的弹窗之上；而钱包连接错误**恰好发生在钱包弹窗打开时**，
所以这一类错误提示在结构上永远不可见。关掉面板后页面只剩同一句「错误代码 USER」，没有指出是格式错误还是网络错误。

### 13.3 服务故障被报成节点失败 —— 实测成立

`app.ts:80` 把两个状态合并成一个 chip：
```js
const ok = conn.node===true && conn.service===true, bad = conn.node===false || conn.service===false;
```
服务地址填 `https://example.com` 后：chip 显示「Testnet 10 · 连接失败，点此处理」，而设置面板里节点一项仍是「已连接 · wss://…」。
用户会以为节点坏了，实际是预算服务不通。

### 13.4 只读收款地址下创建按钮未禁用 —— 实测成立，并修正了成因

实测：用 `kaspatest:…` 收款地址连接后，钱包按钮显示「· 仅收款」，进创建页 → `{ text: '连接钱包后创建', disabled: false }`。

成因与我的初读不同：`views.ts:126` 的 `disabled` 只由 **`p.ok`（表单校验）** 决定，与钱包/服务无关（`p = parseCreate(f)`）。
`onCreate()`（`app.ts:192-196`）在钱包不是 key 类型时**只是重新打开钱包弹窗**，不解释原因。
所以现象是：按钮可点、文案说「连接钱包后创建」（其实钱包已连，只是类型不对）、点击后弹窗重开且无说明。

### 13.5 「已核对」绿标在换节点后不失效 —— 源码判定

`verify` 是内存 Map（`app.ts:27`），只在两处删除：
- `app.ts:200`：通过**分享链接加入**时（`verify.delete(cid)`）；
- `app.ts:178`：另一条导入路径。

**文件导入（`onImportFile`）与切换节点/断开钱包都不会清除它。** 这正好解释了第 8.3 节的实测结果（文件导入伪造状态后绿标仍在），
并推出同一缺陷的第二个入口：换到另一个节点后，旧节点上的核对结论仍然显示为「本机记录与链上状态一致」。

### 13.6 复核说明

我在 13.4 上最初根据 `gate()` 推断按钮会被禁用，实测否证——`gate()` 只在点击后的流程里用，不驱动 `disabled`。
以实测为准。

### 16.2 补充（2026-11-15）：本机节点的真实交易验证、内存限额、与一个界面标签问题

**本机节点能收发交易**：场景 1（空轮）经本机节点（`wss://cd311.cn:888/www/rolling-tn10/node`）跑通，2 笔交易（GENESIS、CLOSE）在本机节点日志里各有一次 `in: 1 via RPC`，事后用只读脚本核对两笔都在选中链上、深度 ≥ 100 DAA（详见 `experiments/rolling/TN10-EVIDENCE.md` §13）。这只证明“本机节点现在接受并打包交易”，一轮 2 笔；256 笔等大规模运行没有在本机节点上做过。

**`MemoryHigh` 调整**：`kaspad-tn10.service` 的 `MemoryHigh` 在运行时由 14G 调到 **17G**（`systemctl set-property --runtime`，未重启，`NRestarts=0`，启动时间不变）。原先提议的 22G 无效：unit 里 `MemoryMax=18G` 是硬上限，`MemoryHigh` 高过它不起作用。依据：该 cgroup 匿名内存 12.8G + 已换出 3.0G，工作集约 15.8G，高于 14G 的限额，所以持续被回收（`memory.events` 的 `high` 累计 179,868 次）。调整后的短暂观察（几分钟）里 `high` 计数没有再涨（179,990 不变），但已换出的 3.0G swap 不会自己换回来，也**没有证据说明这与交易问题有关**。回退：`systemctl set-property --runtime kaspad-tn10.service MemoryHigh=14G`；运行时设置在重启后失效，unit 文件仍是 14G，要永久生效需要改 `/etc/systemd/system/kaspad-tn10.service`（没有改）。

**发现的页面问题（已在 2026-11-15 修复并发布，构建 `75c0ca4c…`）**：轮次页右侧“创建交易”显示的是 `r.origin.transactionId`，即 GENESIS 交易**第一个输入的前置输出**所在的交易（合约创世输出 / 资金来源），不是 GENESIS 交易本身，并且链接到区块浏览器的这个 txid。场景 1 里页面显示 `55ee331e…8cae37`，而交易表中的 GENESIS 是 `ba7113d6…1b3648`。需要改为取 GENESIS 收据的 txid（`views.ts` 约第 269 行）。

### 16.3 补充（2026-11-15）：双花冲突在真实节点上的测试

用户要求对“双花交易这种情况”做测试。同一钱包、两个独立页面、本机节点、真实交易（18 笔、0.18 TKAS），详见 `experiments/rolling/TN10-EVIDENCE.md` §14，脚本 `tests/rolling-web/double-spend.mjs`。结论：

- **两页同时发送**：节点收一笔、拒一笔，原文为 `output (txid, 1) already spent by transaction … in the mempool`；输家页面把它识别为“钱包资金输入被占用”，指出的占用方交易就是赢家的 txid，放弃后第一次重新创建就成功；节点只读核对被拒的那笔既未被接受也不在内存池。这正是 §16 里被页面误判成“别人抢先操作了同一轮”的那类情形，现在给出的是正确的说明和出路。
- **预防**：赢家的交易在内存池里的约 2 秒内，另一页准备交易，3 次都没有冲突；其中 2 次读了链上输入，另一页都避开了赢家已花的输入（旧算法会选它），第 1 次没有读输入。没有对旧版页面做同样时序的对照。
- **旧报价在对方被确认之后发送**：页面在发送前就以 `STALE_INPUT` 拦下，没有任何东西到达节点；界面只给一句“交易没有发出，请重试。”，**没有说明原因**，也没有留下悬空的意图。这是体验上可以改进的地方，没有改。
- **没有覆盖**：`WALLET_FUNDS_PENDING` 提示（测试钱包有 522 个 UTXO，凑得出别的资金）与 `ORPHAN` 分类在真实节点上都没出现过；只测了 GENESIS；§16 中关于“孤儿来自公共节点负载均衡”的推测仍未证实（阶段 3 显示：输入已被已确认交易花掉时，页面发送前就拦下，不会走到节点的孤儿拒绝）。

### 16.4 补充（2026-11-15）：轮次自己的 UTXO 被双花（用户更正了测试对象）

§16.3 测的是“同一个钱包的资金输入”冲突；用户指出要测的是**轮次的 UTXO（管理 UTXO）被双花**。两个买家（不同钱包）同时买同一轮，真实页面、本机节点，详见 `experiments/rolling/TN10-EVIDENCE.md` §15，脚本 `tests/rolling-web/round-double-spend.mjs`。

- **识别**：4 次真实冲突，页面都分类为 `ROUND_INPUT`，占用方交易等于赢家的 txid，被争输出等于赢家交易的第 0 个输入（管理 UTXO），面板和日志都说明原因；被拒的那笔未上链。
- **出路**：放弃 → 导入赢家的最新状态 → 重新买，成功并接在赢家之后（链上核对）。

- **没有覆盖**：只测了 BUY；跨节点真竞争；其它动作的同时发送。
